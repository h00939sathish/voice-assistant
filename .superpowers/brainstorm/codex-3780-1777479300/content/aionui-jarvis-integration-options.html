How should AionUi connect to Jarvis?

Three practical shapes for using AionUi as the face, voice entry point, and mascot layer while preserving the existing Jarvis assistant core.

A. AionUi as remote control
AionUi chat + pet
→
Jarvis API
chat / speak / state

API Bridge

AionUi sends text commands to Jarvis over HTTP/WebSocket. Jarvis keeps wake word, tools, memory, TTS, and safety gates.

B. AionUi as visual companion
Jarvis voice loop
mic / STT / TTS
↔
AionUi pet
listening / thinking / speaking

Pet Companion

Jarvis remains the main interface. AionUi pet mirrors assistant state, expressions, notifications, and quick actions.

C. AionUi as primary desktop shell
AionUi voice/chat/pet
→
Jarvis tools
skills / memory / agents

Frontend Swap

AionUi becomes the main user surface. Jarvis is treated mostly as a backend/tool runtime behind it.

My lean

  • Start with B, then add A if you want typed/remote control.
  • This preserves Jarvis's working voice pipeline and avoids rewiring everything at once.

Watchouts

  • C is highest risk because it changes the primary control loop.
  • Voice input through AionUi depends on what its pet/voice APIs expose cleanly.
